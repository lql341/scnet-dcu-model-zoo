本轮最重要的判断修正

我之前把 Could not find CUDA installation 当成「正常的降级路径」， 并据此推出「当年能跑是因为 JIT 失败了」。这个因果是错的：DTK 是 HIP/ROCm 体系， 那句报错是 Triton 找不到工具链时的误报。真正的区别是——当年 JIT 编译失败所以走了备用路径， 现在编译成功了，但编出来的 kernel 在 gfx936 上访存越界。 把「缺陷」当成「设计」记录下来，是这轮最值得警惕的错误。

02真正拿到的提升

两处都是「早已实测有效、但从未落到交付配置」的项。改动量各一两行。

Kimi-Linear-48B × SGLang：chunked-prefill 4096

16K 输入时 prefill 会一次塞进巨量 token，把 decode 挤到边上。 切成 4096 一片后，prefill 与 decode 能交错执行，KV 压力更平滑。

16K / c8 124.31 137.30 +10.5% 超出噪声，有效
16K / c64 222.45 228.40 +2.7% 本档波动 ±5%，不可区分

辅助指标方向一致：16K/c64 的平均 TTFT 从 101.7 s 降到 91.2 s（−10%）， p99 从 188.6 s 降到 172.3 s。

为什么不改 meta.throughput

本次 A 档的 c64 是 222.45，比历史归档的 234.17 低 5%。本档历史波动本来就有 ±5%， 所以 +2.7% 无法与噪声区分。直接把 228.40 写进基准值，会把节点偏差固化成「官方数据」。 保留 234.17，只把 chunked 的影响幅度写进 README。

04两个被查清的根因

A. Kimi 16K/c64 崩溃：进程累计状态，不是配置问题

现象是「第一轮永远通过、第二轮永远 KERNEL VMFault」。为此先后试过五个配置： 默认、--enforce-eager、--max-num-seqs 24 / 16 / 32+eager。 五个配置、五个崩溃点（29 / 62 / 23 / 16 / 31 个请求），与并发上限毫无关系。

重读 job 1120618 的 3 MB 日志才看清：那次作业用一个服务进程连跑 6 档序列， 10:30 启动、11:02:58 才崩，期间跑完 10 个档位、约 1200 个请求。 而后续作业只跑 16K/c64 一档（128 请求 ≈ 10 分钟），于是表现为「第二轮必崩」。

解法与代价

每轮压测前重启服务进程。实测连续四轮各 128/128、0 处 VMFault。 代价是每轮多 3–4 分钟冷启动。

B. Kimi vLLM 4K/c1 落后 61%：每步 24 ms 的固定气泡

这个缺口我一开始猜成「低并发时 kernel 效率差」。把 TPOT 拆开看，猜错了。

配置vLLM TPOTSGLang TPOT含义
4K / c124.18 ms9.31 ms起点差距
4K / c824.96 ms20.97 msvLLM 几乎不动
16K / c125.23 ms—对 context 也不敏感

vLLM 每步先付 ~24 ms 固定开销，之后加请求几乎免费（拟合 24.07 + 0.111 ms/req）； SGLang 每步只付 7.6 ms，但每请求要加 1.67 ms（7.64 + 1.67 ms/req）。 这就是为什么并发越高 vLLM 越占优、单流却大幅落后。

24 ms ÷ 27 层 ≈ 0.89 ms/层，对得上逐层 eager kernel launch + TP=4 all-reduce。机理线索在启动日志里：

CUDAGraphMode.FULL_AND_PIECEWISE is not supported with
  TritonMLABackend backend (support: AttentionCGSupport.NEVER);
  setting cudagraph_mode=PIECEWISE

AttentionCGSupport.NEVER 意味着 MLA 层的 decode 注意力永远进不了整图， 只能 piecewise 捕获，其余部分每步 eager 发射。Kimi 有 7 层 MLA，直接命中。

与 gotcha #21 的区别

#21 讲的是 MiMo × vLLM 的 16K 档慢 5–7 倍，根因是 DCU 缺 paged-attention kernel， TPOT 从 47.9 ms 涨到 119.3 ms——context 相关。 Kimi 这个是 TPOT 恒定 24 ms——context 无关。 两者根因不同，不能套用同一个结论。

最可能的根因

tvm-ffi 的 JIT KV-cache 路径。11-02 那次 _find_rocm_home() 没识别到 HIP 工具链，抛 Could not find CUDA installation， can_use_store_cache=False，回落 k_cache[indices] = k，一切正常。 现在 ROCM_PATH=/opt/dtk 被识别，JIT 编成，走进新路径，产出在 gfx936 上越界的 kernel。

为什么不再投入

交付不依赖这条路——两个条目的 vLLM 兄弟条目已在 2026-11-12 产出完整 6 档数据。 而每轮诊断都要重载 8.5 GB 镜像，节点根盘水位在 0–278 GB 间波动，多次因磁盘失败。 本想做的 chunked 扫描预期只有几个百分点，且这两个条目受单卡 KV 上限压制 （33 万 tokens vs 64×17K 需 111 万）。

06测试方法

压测口径

6 档 = 输入 4K/16K × 输出 1K × 并发 1/8/64，每档两轮。 客户端统一用 sglang.benchmark.serving，vLLM 条目也用同一个（双容器，保证可比）。

随机 token 负载，不需要下载数据集。

有效性校验

必须 mean_ttft_ms != 0 且吞吐不超物理上限，否则判 INVALID 拒绝入库。

这套校验此前从未真正执行过——heredoc 里两处 bug（os 未导入、 ILENS 未定义），已于本轮修复。

判定规则

变体对比统一阈值：>2% 视为有效，±2% 内视为噪声， 更差则记录撤销。但本档历史波动如果本身有 ±5%，2% 的改善就不该当确定结论。

AB 对照纪律

A 与 B 必须在同一节点、同一镜像、同一时段跑， 且用同作业内的 A 数据做分母，不能拿历史归档值比。

07调优经验

59 条踩坑里挑出最值钱的。完整清单在 docs/gotchas.md。

一、先分离变量，再谈根因

Kimi 16K/c64 那次，我沿着「批大小太大」这个最直觉的解释连开三个作业降 --max-num-seqs，全部失败。真因是进程累计状态，一个「每轮重启」的实验就能分离出来。

教训：当一个现象有多个竞争假设时，先设计能区分它们的实验， 而不是沿着最直觉的那个方向加码。

二、置信区间比数字本身重要

单轮成功不能作为「问题已解决」的证据——本仓库曾据此误记「已跑通」，被第二轮推翻。 反过来，「第二轮必崩」也曾被误读成「批大小问题」。

现在所有变体对比都要求：同节点、同时段、A/B 同作业内对照， 且要报告本档历史波动幅度。Kimi c64 的 +2.7% 就是因此没被当成确定收益。

三、参数失效不会报错

审计 20 个条目后发现三类静默失效，共同点是没有任何报错：

类型实例后果
同一变量 export 两次 EXTRA_ARGS 在 env.sh 里被覆盖 前一行整个失效
启动命令不引用变量 submit.slurm 内联参数，grep EXTRA_ARGS 计数 0 改 env.sh 完全无效
日志写到仓库外 服务端日志落 $WORK/server-$JID.log 无法核对生效值

最严重的后果：env.sh 里写着「必须显式 --attention-backend triton 否则首个 decode 请求崩溃」，而这条从未执行过——服务能跑只是因为后来换成了 0.21 镜像， 那个限制本来就不存在。

四、磁盘是基础设施问题，不是小事

我这一轮把登录节点从 84% 灌到 99%（只剩 15 GB）， 留下 /tmp/pr-insp3 单目录 31 GB。至少 3 次作业因 no space left 失败。

两条硬约束（实测）

镜像存储只能放节点本地——NFS 家目录上 overlay 报 lsetxattr: operation not supported，vfs 报 pivot_root: permission denied。

数据必须放家目录（/public/home/luql，432 GB）， 不要放节点本地 /tmp。而且清理 podman 目录时普通 rm -rf 删不掉 （uid 映射），必须先 podman rmi -af + system prune。

五、「官方未下发」是假设，不是事实

11 个 T01/T02 条目的 §6 曾全部挂 [BLOCKED]，22 个文件写了 44 处「官方未下发」。 官方澄清后我第一反应是「取来公开分数填进去就能跑通」——也错了。

shot模型指标

0-shot instruct 的成绩去比 8-shot base 的分数，差出来的每一分都可能是 shot 数或模型版本造成的。 减出来的「劣化」不是硬件/框架的锅，但它会以「劣化 ≤2pt → 通过」的形式写进 README。 这比不填数字更糟，因为它看起来像通过了验收。

六、别把缺陷当设计

这轮最大的认知错误：看到 Failed to load JIT KV-Cache kernel ... Could not find CUDA installation 这行日志，我推断「当年能跑是因为它失败了，所以是正常的降级路径」。

DTK 是 HIP/ROCm 体系，根本没有 CUDA——那句报错是 Triton 找不到工具链的误报。 正确做法是让它指向 DTK 的编译器，而不是依赖「编译失败」侥幸能跑。 把缺陷写进文档当经验，会让下一个人沿着错误的方向优化。

09留给下一个人的

可以继续推进的

Recon/RoboBrain × vLLM 的参数扫描：这两个条目 optimized=false， 从没扫过 chunked_prefill_size（当前是默认 8192）。 SGLang 侧已封存，vLLM 侧是唯一可动的路。

Kimi vLLM 4K/c1 的三个候选参数：--compilation-config、 --async-scheduling、RCCL 调优。实验脚本已就绪，作业 1128368。

不建议再碰的

MiMo × vLLM 16K 档：三轮扫描含 v0 引擎全无效，缺 paged-attention kernel， 只能自建镜像。

fp8 / 量化：torch.addmm 对 Float8 直接 NotImplementedError， 一行代码可复现。

Wan 8 卡：FSDP 4→8 卡只有 1.11×，已饱和；数据并行分片单卡必 OOM。

重新打开 Recon/RoboBrain 的两种做法

如果将来确实需要，按成功率从高到低试：

  1. export TVM_FFI_GPU_BACKEND=cuda（务必无 CUDA_HOME）→ 强制复刻「JIT 失败、回落」状态。估 60–70%。
  2. rm -rf ~/.triton/cache + TRITON_CACHE_DIR 指向本地 + TRITON_ALWAYS_COMPILE=1 → 排除陈旧 hsaco。估 35–45%。
