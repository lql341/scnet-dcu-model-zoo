# vLLM 长上下文专项扫描（2026-11-03）：结论是「配置改不动」

背景：同模型同卡，vLLM 在 16K 档比 SGLang 慢 5–7 倍（`bench/summary.md` vs MiMo-SGLang 条目）。
本文件记录三轮扫描的**实测结果与阴性结论**，避免下次重复烧卡时。

## 初始症状（来自 `logs/server.log` 与 bench）

| 档位 | vLLM | MiMo×SGLang | 差距 |
| --- | --- | --- | --- |
| 4K/c1 | 20.73 | 44.31 | −53% |
| 16K/c1 | 8.19 | 41.47 | −80% |
| 16K/c8 | 44.83 | 308.72 | −85% |
| 16K/c64 | 100.82 | 299.81 | −66% |

启动日志里唯一的异常线索：

```
WARNING [chunked_prefill_paged_decode.py:400]
Cannot use ROCm custom paged attention kernel, falling back to Triton implementation.
```

16K 时 TPOT 从 47.9 ms（4K）涨到 119.3 ms，而 SGLang 只有 ~24 ms —— 瓶颈在**逐 token 的
paged decode 注意力**，不是 prefill。

## 第一轮（`sweep/sweep_16k.slurm`，失败，留作教训）

把服务与压测客户端放同一容器 → 三档全失败：
`ModuleNotFoundError: No module named 'sglang'`（vLLM 镜像不含 sglang 压测器）。
**教训：vLLM 条目的压测必须在 SGLang 镜像里跑**（`container/submit.slurm` 本来就是双容器，扫描脚本没照抄）。

## 第二轮（`sweep/sweep_16k2.slurm`，1.5 h，2 卡）

| 变体 | 16K/c1 (tok/s) | 16K/c8 (tok/s) | 4K/c64 (tok/s) |
| --- | --- | --- | --- |
| X1 base（mns 128, mem 0.95） | 8.20 | 44.88 | 491.44 |
| X2 `--max-num-batched-tokens 8192` | 8.21 | 48.83 | 504.41 |
| X3 `--max-num-batched-tokens 2048` | 8.20 | 44.91 | 492.27 |
| X4 `VLLM_ROCM_USE_AITER=1` | 8.20 | 44.92 | 492.28 |
| X5 `--tensor-parallel-size 2` | 启动失败 | — | — |

- **prefill 切片大小完全无影响**（本来就默认开 chunked prefill）
- **AITER 开关无影响**：`Cannot use ROCm custom paged attention kernel` 警告依然出现，
  说明该内核在这套 DTK/torch 组合下根本不可用，不是环境变量能打开的
- X5 失败根因：`local_world_size (2) must be <= visible devices (1)`
  —— podman 不继承 Slurm 的 `HIP_VISIBLE_DEVICES`，容器里只看到 1 张卡（**这是新踩的坑**）

## 第三轮（`sweep/sweep_16k3.slurm`，1.5 h，2 卡）

修掉可见性透传后，改测真正能影响 decode 的两个旋钮：

| 变体 | 16K/c1 | 16K/c8 |
| --- | --- | --- |
| Y1 `VLLM_ATTENTION_BACKEND=FLASH_ATTN` | 8.17 | 44.76 |
| Y2 `--kv-cache-dtype fp8` | 7.60 | 34.43（**更差**） |
| Y3 FLASH_ATTN + fp8 KV | 7.61 | 34.48（同样更差） |
| Y4 TP=2（透传可见性后） | 仍然启动失败 | — |

- 后端覆盖无效（vLLM 在 ROCm 上仍走 Triton paged decode）
- **fp8 KV 在这张卡上是负优化**（TPOT 119→127 ms）：量化/反量化开销大于带宽收益
- TP=2 需要继续查（worker `init_device` 仍失败，详见 `server-Y4_tp2.log`）

## 结论（可复现）

**在 vLLM 0.20 + 这套 DCU 镜像上，16K 档的 5–7 倍差距不是参数问题**：
chunked-prefill 大小、AITER、attention backend 覆盖、fp8 KV、TP=2 五条路都试过，
没有一条能改善 decode 的 TPOT。要真正补上，只能走「自己构建镜像」：

1. 编译/启用 DCU 版 paged-attention 内核（`VLLM_ROCM_USE_AITER` 之外的路径，aiter 需重编）；
2. 或退回 v0 引擎（`VLLM_USE_V1=0`）对比 —— 未测，成本 ~0.5 卡时；
3. 或换 SGLang 部署该模型（本仓库已有同模型 SGLang 条目，16K/c8 308.72 tok/s）。

这也直接支撑了项目的下一步：**要归档自己的镜像**，而不是永远依赖 `dcu/linshp` 的公共镜像。
